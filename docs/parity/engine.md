# The OpenSearch engine (M5)

[Index](../parity.md). Pinned OpenSearch: **3.8.0**. How the engine is put
together, what it refuses and where it behaves differently:
[`docs/opensearch-engine.md`](../opensearch-engine.md). Rows here are the
writer features the engine needed, whichever crate they live in; the C-ABI
writer outside the engine is [ffi.md](ffi.md).

| Java | Rust | Status |
|---|---|---|
| `index/IndexWriter.softUpdateDocuments` / `updateDocValues` (soft-deletes **write** side) | `lucene-index/src/index_writer/explicit.rs::{soft_update_explicit_documents, update_explicit_documents}`, `lucene-index/src/field_updates.rs` | **ported** M5. A soft update adds the new documents and applies the doc-values updates to every earlier match of the term, atomically, first. Updates resolve their field **by name** per segment and are written under that segment's own number; compound segments are updated through the `.cfs`. An update to an unregistered field is refused (`verifyOrCreateDvOnlyField`); `softDelCount` is re-counted when deletes or doc values change. |
| `index/SoftDeletesRetentionMergePolicy` (OpenSearch's retention query `_seq_no >= minRetainedSeqNo`) | `lucene-index/src/index_writer.rs::{SoftDeletesRetention, apply_soft_deletes_retention, set_soft_deletes_retention}` | **ported** M5. A merge keeps a soft-deleted document only while its `_seq_no` doc value is retained (none: never). `force_merge(1)` rewrites a single segment only when it holds reclaimable deletes; `force_merge_deletes` takes segments above 10% reclaimable deletes, in one merge rather than Java's size-bounded groups. Without a policy every soft-deleted document is kept; the engine always sets one. |
| OpenSearch `index/engine/PrunePostingsMergePolicy` | `SoftDeletesRetention::prune_postings_field`, `lucene-index/src/merge.rs::SourcePostings` | **ported** M5. A retention merge drops the `_id` postings of every soft-deleted document it carries over; a term left without documents is dropped, a field left without terms is not written. |
| OpenSearch `index/engine/RecoverySourcePruneMergePolicy` | `SoftDeletesRetention::prune_recovery_source_field`, `lucene-index/src/merge.rs::PrunedField` | **ported** M5. `_recovery_source` (stored field and NUMERIC doc value) survives a merge only on documents the retention query matches; such a source merges through the visitor stored-fields path, as Java's filtering reader forces. |
| `index/IndexWriter.MAX_DOCS` / `reserveDocs` / `setMaxDocs` | `lucene-index/src/index_writer.rs::{MAX_DOCS, reserve_docs, set_max_docs}` | **ported** M5. Every add path counts every segment's documents plus the buffered ones and refuses past the limit, before buffering anything, with Java's message; the engine passes the JVM's `maxDocs`. Not yet enforced by `concurrent_writer`. |
| `codecs/lucene90/Lucene90DocValuesConsumer.writeSkipIndex` (doc-values skip index, `.dvs`) | `lucene-codecs/src/doc_values.rs::{write_fields_with_skip_indexes, write_skip_index, write_skip_levels}`, `lucene-codecs/src/doc_values_updates.rs::write_numeric_generation_with_skip_index` | **ported** M5: NUMERIC, SORTED_NUMERIC, SORTED and SORTED_SET, dense or sparse, at flush, merge and in an update's generation. Byte-identical to Java's `.dvs` and `.dvm` summary on the 36,000-document multi-level fixture and on `GenDocValuesSkipIndexShapes` (`tests/doc_values_skip_index_fixtures.rs`); `EngineWriterDiffTest` walks every skipper level through Lucene's reader. **Not yet benchmarked** (no `bench-micro.sh` pair): stage 3 is open; it runs once per skip-indexed field per flush and merge. |
| `codecs/DocValuesConsumer.mergeSortedField` / `mergeSortedSetField` (live-terms filtering) | `lucene-index/src/merge.rs::{OrdinalMap::build, live_ords}` | **ported** M5. A source with deletions contributes only the ordinals its live documents use (`BitsFilteredTermsEnum`), so no ordinal holes. |
| `index/IndexWriter.forceMerge` / `forceMergeDeletes`, `IndexFileDeleter` driven by a caller's deletion policy | `lucene-index/src/index_writer.rs::{force_merge, force_merge_deletes, commit_generations, delete_commits, hold_commit, release_files}` | **ported** M5. OpenSearch's `CombinedDeletionPolicy` runs in Java and names the commits to drop; a reader's hold keeps a dropped commit's files until it closes. |
| `codecs/lucene90/Lucene90DocValuesConsumer` SORTED_SET single-valued shape | `lucene-codecs/src/doc_values.rs` | **ported** M5. A SORTED_SET column where every document with a value has one is written single-valued (SORTED), as Java does. |
| `index/SegmentMerger` postings for a field one source declares without terms | `lucene-index/src/merge.rs::merge_postings` | **ported** M5. Such a source contributes nothing (`MultiFields`). |
| OpenSearch `index/engine/InternalEngine` | `opensearch-plugin/.../engine/RustEngine.java` (derived by `opensearch-plugin/tools/derive_engine.py`), `lucene-ffi/src/engine_writer.rs` | **ported** M5, Java + Rust: `InternalEngine` copied from 3.8.0 with only the writer swapped; documents inverted in Java (`DocumentEncoder`), written by the Rust writer; refresh is a Rust commit; merges inside `ffi_engine_writer_commit` and `ffi_engine_writer_force_merge`. OpenSearch's `InternalEngineTests` on it (`scripts/opensearch-engine-tests.sh`): 117 pass, 34 skipped with reasons. Segment-replication primary via `RustIndexerFactory` (refresh checkpoints for `RustEngine`); remote-backed storage refused. |
| `index/FreqProxTermsWriterPerField.writeProx` payloads + `FieldInfo.setStorePayloads` on explicit documents | `lucene-index/src/index_writer/explicit.rs::{InvertedTerm, build_and_write_explicit_segment}`, `lucene-ffi/src/engine_writer.rs` (term flag 4), `opensearch-plugin/.../engine/DocumentEncoder.java` | **ported** M5. Each occurrence's payload is sent and written (fields with positions only), and a field stores payloads in exactly the segments where a document gave it a non-empty one, as in Java; a merge decodes each source with its own `store_payloads` and ORs them. `EngineWriterDiffTest` compares payloads occurrence by occurrence against Lucene's `IndexWriter`. |
