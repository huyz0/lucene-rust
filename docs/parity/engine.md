# The OpenSearch engine (M5)

[Index](../parity.md). Pinned OpenSearch: **3.8.0**. How the engine is put
together, what it refuses and where it behaves differently:
[`docs/opensearch-engine.md`](../opensearch-engine.md). Rows here are the
writer features the engine needed, whichever crate they live in; the C-ABI
writer outside the engine is [ffi.md](ffi.md).

| Java | Rust | Status |
|---|---|---|
| `index/IndexWriter.softUpdateDocuments` / `updateDocValues` (soft-deletes **write** side) | `lucene-index/src/index_writer/explicit.rs::{soft_update_explicit_documents, update_explicit_documents}`, `lucene-index/src/field_updates.rs` | **ported** M5. A soft update adds the new documents and applies the doc-values updates to every earlier match of the term, atomically, before the new documents. Updates resolve their field **by name** in each segment (a segment Java wrote, or one a merge renumbered, may number it differently) and are written under that segment's own number; compound segments are updated by reading their base files through the `.cfs` (`CompoundReader`). `verifyOrCreateDvOnlyField`: an update to an unregistered field is refused. `softDelCount` is re-counted per segment when its deletes or doc values change. |
| `index/SoftDeletesRetentionMergePolicy` (OpenSearch's retention query `_seq_no >= minRetainedSeqNo`) | `lucene-index/src/index_writer.rs::{SoftDeletesRetention, apply_soft_deletes_retention, set_soft_deletes_retention}` | **ported** M5. A merge keeps a soft-deleted document only while its `_seq_no` doc value is retained; one without a `_seq_no` is never retained. `force_merge(1)` on a single segment rewrites it only when it holds reclaimable deletes (`MergePolicy.numDeletesToMerge`: hard deletes plus soft deletes retention no longer keeps), and `force_merge_deletes` takes a segment only above `forceMergeDeletesPctAllowed` (10%) of reclaimable deletes (`TieredMergePolicy.findForcedDeletesMerges`), in one merge rather than Java's size-bounded groups. Without a retention policy the writer keeps every soft-deleted document -- the engine always sets one. |
| OpenSearch `index/engine/PrunePostingsMergePolicy` | `SoftDeletesRetention::prune_postings_field`, `lucene-index/src/merge.rs::SourcePostings` | **ported** M5. A retention merge drops the `_id` postings of every soft-deleted document it carries over; a term left without documents is dropped, a field left without terms is not written. |
| OpenSearch `index/engine/RecoverySourcePruneMergePolicy` | `SoftDeletesRetention::prune_recovery_source_field`, `lucene-index/src/merge.rs::PrunedField` | **ported** M5. `_recovery_source` (stored field, plus the NUMERIC doc value of the same name) survives a merge only on documents the retention query matches; a source with such a document is merged through the visitor stored-fields path, as Java's filtering reader forces. |
| `index/IndexWriter.MAX_DOCS` / `reserveDocs` / `setMaxDocs` | `lucene-index/src/index_writer.rs::{MAX_DOCS, reserve_docs, set_max_docs}` | **ported** M5. Every add path counts all documents of every segment plus the buffered ones (deleted documents count until a merge drops them) and refuses, before buffering anything -- its own delete included -- past the limit, with Java's message. The engine passes the JVM engine's `maxDocs`. Not yet enforced by `concurrent_writer`. |
| `codecs/lucene90/Lucene90DocValuesConsumer.writeSkipIndex` (doc-values skip index, `.dvs`) | `lucene-codecs/src/doc_values.rs::{write_fields_with_skip_indexes, write_skip_index, write_skip_levels}`, `lucene-codecs/src/doc_values_updates.rs::write_numeric_generation_with_skip_index` | **ported** M5. NUMERIC, SORTED_NUMERIC, SORTED and SORTED_SET, dense or sparse; at flush, at merge and in a doc-values update's generation. Byte-identical to Java's `.dvs` and `.dvm` summary on the 36 000-document multi-level fixture, and field by field on `GenDocValuesSkipIndexShapes` (a constant run past one interval, sparse SORTED, sparse multi-valued and single-valued SORTED_SET, multi-valued SORTED_NUMERIC) -- `tests/doc_values_skip_index_fixtures.rs`; `EngineWriterDiffTest` walks every interval at every level of the Rust index's skippers through Lucene's reader against the true values (Lucene's `CheckIndex` checks only the skipper's shape). The update path's former `SkipIndexUnsupported` refusal is gone. OpenSearch 3.8 gives `@timestamp` a skip index. **Not yet benchmarked** against `Lucene90DocValuesConsumer` (no `bench-micro.sh` pair): stage 3 of the port workflow is open for this writer; it runs once per skip-indexed field per flush and merge, over values already in memory. |
| `codecs/DocValuesConsumer.mergeSortedField` / `mergeSortedSetField` (live-terms filtering) | `lucene-index/src/merge.rs::{OrdinalMap::build, live_ords}` | **ported** M5 (fix). A source with deletions contributes only the ordinals its live documents use (`BitsFilteredTermsEnum`); before this a merge kept terms only deleted documents had carried, which Java's `CheckIndex` rejects as ordinal holes. |
| `index/IndexWriter.forceMerge` / `forceMergeDeletes`, `IndexFileDeleter` driven by a caller's deletion policy | `lucene-index/src/index_writer.rs::{force_merge, force_merge_deletes, commit_generations, delete_commits, hold_commit, release_files}` | **ported** M5. OpenSearch's `CombinedDeletionPolicy` runs in Java and names the commits to drop; a reader's hold keeps a dropped commit's files until it closes. |
| `codecs/lucene90/Lucene90DocValuesConsumer` SORTED_SET single-valued shape | `lucene-codecs/src/doc_values.rs` | **ported** M5 (fix). A SORTED_SET column in which every document with a value has exactly one is written in the single-valued (SORTED) shape, as Java does; Lucene's reader dereferenced a missing multi-valued address table otherwise. |
| `index/SegmentMerger` postings for a field one source declares without terms | `lucene-index/src/merge.rs::merge_postings` | **ported** M5 (fix). Such a source contributes nothing (`MultiFields`), instead of refusing the merge (`PostingsFieldMissingInSource` is gone). |
| OpenSearch `index/engine/InternalEngine` | `opensearch-plugin/.../engine/RustEngine.java` (derived by `opensearch-plugin/tools/derive_engine.py`), `lucene-ffi/src/engine_writer.rs` | **ported** M5, Java + Rust. `InternalEngine` copied from 3.8.0 with only the writer swapped; documents inverted in Java (`DocumentEncoder`) and written by the Rust writer; refresh is a Rust commit. Merges cross the boundary inside `ffi_engine_writer_commit` and as `ffi_engine_writer_force_merge` (`IndexWriter::apply_merge` itself is not wrapped). OpenSearch's own `InternalEngineTests` run on it (`scripts/opensearch-engine-tests.sh`): 117 pass, 34 skipped with a reason each. A segment-replication primary too: `RustIndexerFactory` swaps each index's indexer factory (in `IndexModule`) so `EngineBackedIndexer`'s refresh checkpoint answers for `RustEngine` (3.8 answers only for `InternalEngine`); remote-backed storage stays refused. |
| `index/FreqProxTermsWriterPerField.writeProx` payloads + `FieldInfo.setStorePayloads` on explicit documents | `lucene-index/src/index_writer/explicit.rs::{InvertedTerm, build_and_write_explicit_segment}`, `lucene-ffi/src/engine_writer.rs` (term flag 4), `opensearch-plugin/.../engine/DocumentEncoder.java` | **ported** M5. The engine used to refuse a document whose analyzer produced a payload; OpenSearch records a refused primary operation as a no-op tombstone, so `InternalEngineTests` lost documents on every seed whose `MockAnalyzer` put payloads on a field (CI: `testAppendConcurrently` `expected:<1024> but was:<6>`, `testStressUpdateSameDocWhileGettingIt`). Now each occurrence's payload is sent and written, only for a field with positions, and a field stores payloads in exactly the segments one of whose documents gave it a non-empty one, as in Java. A merge decodes each source with that source's own `store_payloads` (it used to take the writer's registered schema, which never has it, and read a payload segment's positions as garbage) and ORs it. `EngineWriterDiffTest` compares payloads occurrence by occurrence against Lucene's `IndexWriter`. |
