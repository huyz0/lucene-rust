# lucene-ffi -- the plugin's native library

[Index](../parity.md). The boundary machinery and the analysis entry points
of the library the OpenSearch plugin calls through FFM. Queries, aggregations,
fetch and the engine writer are in [plugin.md](plugin.md) and
[engine.md](engine.md). Conventions: opaque `u64` handles, `guard`
(`catch_unwind`) around every body, `lock_recovering`.

| Java | Rust | Status |
|---|---|---|
| (none: Rust-only) the analysis modules on the plugin's classpath | `lucene-ffi/src/analysis_modules.rs::{register, ffi_add_data_pack_dir}`; Cargo features `analysis-*`, `embedded-data` | **ported** (no Java counterpart; Java's `ServiceLoader` sees the module jars): kuromoji, nori, smartcn, stempel, morfologik, phonetic and ICU register their factories before the first analyzer spec is built, each behind a feature (all on). Their dictionaries are data packs, not compiled in unless `embedded-data`; the plugin adds `<config>/lucene-rust/packs` and its own `packs/` (ABI 55) and offers `rust_japanese`, `rust_korean`, `rust_chinese` (`RustAnalysis`), registered only when their pack is there (OpenSearch builds every registered tokenizer for every index). Tests: `analysis_modules` and `jvm_analysis` unit tests (a spec refused without the pack, Lucene's tokens with it); `NativeSelfTestAnalysis.packs`. |
| -- (the boundary itself: handles) | `lucene-ffi/src/handle.rs::{SlotMap, RegistryTag}`, `lucene-ffi/src/registry.rs::{lock_recovering, read_recovering}`, `lucene-ffi/src/raw.rs` | **rust-only**: opaque `u64` handles (tag, generation, index) from a generation-tagged slotmap; a stale, closed or cross-registry handle is refused. Tests: `handle.rs`, `registry.rs`, `tests/resource_bounds.rs`. |
| -- (panic containment and errors) | `lucene-ffi/src/error.rs::{FfiStatus, guard}`, `lucene-ffi/src/ffm_bridge.rs::ffi_jvm_last_error` | **rust-only**: `guard` = `catch_unwind` -> `FfiStatus::Panic` plus a thread-local last-error message (panic text from a hook); every non-`Ok` status leaves a message about that call. Tests: `error.rs`. |
| `analysis/custom/CustomAnalyzer` built from a running analyzer's chain, for the plugin | `lucene-ffi/src/jvm_analysis.rs::{analyzer, analyze}`, `ffm_bridge.rs::ffi_jvm_analyze_alloc`; Java `AnalyzerSpec` | **ported** (ABI 47). The plugin reflects the char filters, tokenizer and token filters an analyzer builds, writes them as SPI names and factory arguments (word lists and mapping rules inline), and Rust builds a `CustomAnalyzer` per distinct spec (cached). Java only uses a spec whose tokens match its own analyzer on fixed probe texts. Synonym maps (graph and old filter) are copied entry for entry and stemmer-override maps line for line. Hunspell dictionaries go as their `.aff`/`.dic` bytes: `HunspellSources` finds the OpenSearch `hunspell` filter factory holding the dictionary and rereads the files its `HunspellService` loaded (locale or `ref_path`), only while the service's cache still holds that very instance; a plugin-supplied dictionary stays in Java (`analysis_hunspell`); OpenSearch's `dedup` goes as the factory's `dedup` extension. Thai: the plugin's `rust_thai` tokenizer and analyzer (`RustTokenizer` over the `RustAnalysis` table, one row per `rust_*` tokenizer) call Rust's `ThaiTokenizer` (ICU's Thai dictionary, `lucene-analysis-icu`) from Java too, so a natively indexed field and the query text OpenSearch analyzes in Java split Thai alike; `AnalyzerSpec` maps any `RustTokenizer` to its SPI name and arguments. **Gap:** Lucene's own `thai` tokenizer and analyzer (the JDK's dictionary, `docs/licences.md`) stay in Java, as do classes not in the mapping table (Huy chose the separate `rust_thai` name 2026-10-30). Tests: `jvm_analysis` unit tests; `NativeSelfTestAnalysis` (48 analyzers, every token attribute against Lucene on probes and random text). |
| `index/IndexingChain` inversion of a text field with an analyzer the plugin registered (`DocumentEncoder.invert` on the Java side) | `lucene-ffi/src/jvm_invert.rs::invert`, `jvm_analysis.rs::register`, `engine_writer.rs::{analyzed_field, ffi_engine_prepare, ffi_engine_writer_apply_prepared}` | **ported** (ABI 47). Java sends the field's raw strings with a registered analyzer id, its index options and norm mode; Rust runs the analyzer, builds positions, offsets, frequencies and the norm the way `IndexingChain` and `BM25Similarity.computeNorm` do (Java int wrapping, the immense-term and zero-norm messages), outside the writer lock. Fields with term vectors, custom token streams, a similarity overriding `computeNorm` or mixed index options stay in Java. Tests: `jvm_invert` unit tests; `EngineWriterDiffTest` seeds 4 and 5 compare segments with Lucene's. |
| `analysis/util/FilesystemResourceLoader`, `analysis/custom/CustomAnalyzer` (configuration from the JVM) | `lucene-analysis/src/factory/loader.rs::FilesystemResourceLoader` | **not-needed** M11: no C-ABI or FFM function builds an analyzer from configuration. **Gap** before one does: confine `FilesystemResourceLoader` to its base directory (it resolves `..` and absolute names as Java) and cap a resource's bytes (it reads whole files), lest boundary-crossing config read any file or exhaust memory. |
