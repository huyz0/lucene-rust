# lucene-ffi -- the plugin's native library

[Index](../parity.md). The boundary machinery and the analysis entry points
of the library the OpenSearch plugin calls through FFM. Queries, aggregations,
fetch and the engine writer are in [plugin.md](plugin.md) and
[engine.md](engine.md). Conventions: opaque `u64` handles, `guard`
(`catch_unwind`) around every body, `lock_recovering`.

| `analysis/custom/CustomAnalyzer` built from a running analyzer's chain, for the plugin | `lucene-engine/src/analysis.rs::{analyzer, analyze}`, `ffm_bridge.rs::ffi_jvm_analyze_alloc`; Java `AnalyzerSpec` | **ported** (ABI 47). The plugin reflects the char filters, tokenizer and token filters an analyzer builds, writes them as SPI names and factory arguments (word lists and mapping rules inline), and Rust builds a `CustomAnalyzer` per distinct spec (cached). Java only uses a spec whose tokens match its own analyzer on fixed probe texts. Synonym maps (graph and old filter) are copied entry for entry and stemmer-override maps line for line. Hunspell dictionaries go as their `.aff`/`.dic` bytes: `HunspellSources` finds the OpenSearch `hunspell` filter factory holding the dictionary and rereads the files its `HunspellService` loaded (locale or `ref_path`), only while the service's cache still holds that very instance; a plugin-supplied dictionary stays in Java (`analysis_hunspell`); OpenSearch's `dedup` goes as the factory's `dedup` extension. Thai: the plugin's `thai_dictionary` tokenizer and analyzer (`RustTokenizer` over the `RustAnalysis` table, one row per `rust_*` tokenizer) call Rust's `ThaiTokenizer` (ICU's Thai dictionary, `lucene-analysis-icu`) from Java too, so a natively indexed field and the query text OpenSearch analyzes in Java split Thai alike; `AnalyzerSpec` maps any `RustTokenizer` to its SPI name and arguments. **Gap:** Lucene's own `thai` tokenizer and analyzer (the JDK's dictionary, `docs/licences.md`) stay in Java, as do classes not in the mapping table (Huy chose the separate `thai_dictionary` name 2026-10-30). Tests: `analysis` unit tests; `NativeSelfTestAnalysis` (56 analyzers, every token attribute against Lucene on probes and random text). |
| `analysis/ja`, `analysis/ko` (kuromoji and nori) chains described for the plugin | `AnalyzerSpec` mappers to `lucene-analysis-kuromoji`, `lucene-analysis-nori` factories | **ported**. OpenSearch's `analysis-kuromoji` and `analysis-nori` plugins build Lucene's classes, so their tokenizers, filters and the iteration-mark char filter map to the Rust factories (the `kuromoji` and `nori` data packs). A user dictionary is written back from the tokenizer's FST and entry arrays as the lines it is read from; one that cannot be written back exactly (a field with a comma, quote or whitespace, or a nori entry whose right id would change) stays in Java (`analysis_japanese_user_dictionary`, `analysis_korean_user_dictionary`), as does a tokenizer on other than the bundled dictionaries. Tests: `NativeSelfTestAnalysis.cjkModules` (eight chains, user dictionaries included). |
| `index/IndexingChain` inversion of a text field with an analyzer the plugin registered (`DocumentEncoder.invert` on the Java side) | `lucene-engine/src/invert.rs::invert`, `lucene-engine/src/analysis.rs::register`, `engine_writer.rs::{analyzed_field, ffi_engine_prepare, ffi_engine_writer_apply_prepared}` | **ported** (ABI 47). Java sends the field's raw strings with a registered analyzer id, its index options and norm mode; Rust runs the analyzer, builds positions, offsets, frequencies and the norm the way `IndexingChain` and `BM25Similarity.computeNorm` do (Java int wrapping, the immense-term and zero-norm messages), outside the writer lock. Fields with term vectors, custom token streams, a similarity overriding `computeNorm` or mixed index options stay in Java. Tests: `invert` unit tests; `EngineWriterDiffTest` seeds 4 and 5 compare segments with Lucene's. |
| `analysis/util/FilesystemResourceLoader`, `analysis/custom/CustomAnalyzer` (configuration from the JVM) | `lucene-analysis/src/factory/loader.rs::FilesystemResourceLoader` | **not-needed** M11: no C-ABI or FFM function builds an analyzer from configuration. **Gap** before one does: confine `FilesystemResourceLoader` to its base directory (it resolves `..` and absolute names as Java) and cap a resource's bytes (it reads whole files), lest boundary-crossing config read any file or exhaust memory. |
