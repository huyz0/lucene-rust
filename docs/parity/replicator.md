# lucene-replicator -- near-real-time index replication (M14 T14.3, M14.e)

[Index](../parity.md). `org.apache.lucene.replicator.nrt`: a primary node turns each NRT point of
its `IndexWriter` into a `CopyState` -- every file's `FileMetaData` (index header, codec footer,
length, checksum) and the `segments_N` bytes naming them -- and replica nodes copy the files they
lack, reference-count them so a file goes only when no point or commit uses it, and open readers
over the copied point. Lucene 10.5.0's replicator is this package alone: the revision replicator
(`Replicator`, `LocalReplicator`, `IndexRevision`, `ReplicationClient`, `SessionToken`, the HTTP
servlet and client) was removed before 10.0 and is not in the jar, so there is nothing of it to
port (`docs/inventory/lucene-replicator.tsv`). How bytes travel between nodes is abstract in Java
(the test framework's `SimplePrimaryNode`/`SimpleReplicaNode` speak a socket protocol); here it is
the `PrimaryHooks`/`ReplicaHooks` traits plus an in-process transport.

Bench (per file over the 25 files of `fixtures/data/replicator/plain`, `scripts/bench-micro.sh --bench replicator`, `ReplicatorMicro.java` vs `micro_replicator.rs`; noise 1.14x, capped container on a shared host): `repl_file_meta` 1.27 us vs 46.5 us (~37x: Java's `MMapDirectory` maps and unmaps each 50-2,500 byte file per `openInput`, Rust reads it whole where Java reads header and footer, so the ratio holds for small files only; not profiled further); `repl_copy_file` 7.25 us vs 19.3 us (~2.7x). The point is copied to a scratch directory first (off the bind mount both sides spent milliseconds per file).
