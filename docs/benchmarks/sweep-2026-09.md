# Performance sweep, September 2026 -- every area against Lucene 10.5.0

**Goal:** for every ported area, a component benchmark that runs the same
operation on this port and on Lucene 10.5.0 over the same bytes, and a port
that is **not slower and uses less memory** in each of them. Where the M1/M1.6
work measured decode kernels and a query mix, this sweep adds the areas that
had no Java counterpart at all (doc values, norms, points, positions, term
dictionary seeks, analysis, bitsets, LZ4, checksums, varints, reader memory)
and fixes what they found.

## Method

- **Machine:** i5-13600KF (hybrid), WSL2 Docker Desktop VM, both engines in the
  `lucene-rust-test` container (`scripts/docker-test.sh`), JDK 21 with
  `--add-modules jdk.incubator.vector` (Panama vectorization live: "preferredBitSize=256; FMA enabled").
- **Corpus:** `scripts/bench-corpus.sh`, 5M documents, merged to one segment,
  on a Docker volume (not a bind mount -- every mmap page fault through a
  Windows bind mount taxes both engines and measures the mount). The corpus now
  stores `title` and an `id`, and adds a `keyword` SORTED doc-values column, so
  stored fields and sorted doc values can be measured at all.
- **Component benchmarks:** `scripts/bench-micro.sh --bench <area>`; the Java
  side is `benchmarks/micro/java/SweepMicro.java` (plus `PForUtilMicro`), the
  Rust side the same-named cases in `benchmarks/rust-runner/src/micro.rs`.
  Every timed call does a batch of work; figures are ns per unit. Three
  interleaved repetitions; a ratio inside the measured noise floor is printed
  with `~` and is not a result.
- **Queries:** `scripts/bench-compare.sh` (28 queries, recall cross-checked
  before any timing is compared).
- **Build:** Linux x86_64 builds target `x86-64-v3` (`.cargo/config.toml`); see
  "Build target" below.
- **Noise:** the host was shared with an unrelated mutation-testing run for
  the whole sweep. Ratios, not absolute qps, are the result; the noise column
  is measured per run.

Ratios are `java_time / rust_time`: **above 1.0 means this port is faster**.

Below 1.0, and why each is left:

- **`FixedBitSet.nextSetBit` walk, 0.96x** (3.28 vs 3.14 ns). Both engines
  run the same serial chain per call -- load the word, mask, `tzcnt`, add the
  word's base, add the caller's `+ 1` -- and are latency-bound on it. C2 folds
  the last two adds into one three-operand `lea`; LLVM's generic x86-64-v3
  tuning avoids that instruction (it is slow on Haswell and Skylake). Proven,
  not guessed: the same code built with `-C target-feature=-slow-3ops-lea`
  runs 2.91 ns, **1.08x Lucene**. That flag is not shipped -- rustc calls it
  unknown and unstable, and it would change code generation everywhere for
  CPUs where the three-operand form is slower -- but a deployment pinned to
  newer cores can build with it. Source-level rewrites that give LLVM a
  reassociable add instead all measured slower (single-return shift form
  4.2 ns, shift form with a first-word branch 3.69, branch-free two-word
  3.82). The engine's own set-bit loops use `for_each_set_bit`, which is well
  ahead.
- **Doc values `numeric_stride37`, 0.91x** (1.98 vs 1.80 ns), against a noise
  floor of 1.10-1.34x for the case; it measured 1.10x in round 10 and
  0.87-0.93x since, and Lucene's own time for it has ranged 1.80-2.33 ns. The
  loop is a strided walk through a 5M-document column and two thirds of its
  profile is one stall on the value load: memory-bound on both sides. Tried:
  folding the document bound into the packed reader's own limit (one compare
  per lookup instead of two; kept, neutral), and a four-byte load instead of
  eight, as Lucene's width-specialized readers make, in case split cache
  lines explained it -- an in-process A/B showed no difference, so it was
  reverted.

_The sections below record what each finding was and what fixed it, in the
order the sweep found them._

## Build target

`.cargo/config.toml` (new in this sweep) builds Linux x86_64 for
`target-cpu=x86-64-v3` (AVX2, FMA, BMI2 -- Haswell, 2013, and later). Every
AVX2 kernel in `lucene_util::simd` and the numbers below depend on it. It is a
**CPU floor for the shipped library**: there is no runtime feature detection
yet, so a binary built this way stops with an illegal-instruction fault on an
x86_64 CPU without AVX2. Other targets (aarch64, non-Linux) are unaffected and
use the scalar kernels. Runtime detection is the open item recorded in
`PLAN.md` Phase 7. The file must be committed with this change -- without it
the kernels compile to their scalar fallbacks and the vector, prefix-sum and
`findNextGEQ` wins disappear.

## What the sweep found, and what fixed it

Each entry names the measured gap, the cause a profile showed, and the change.
"Lucene does X" is from reading the 10.5.0 source, not from memory.

### Query execution

- **Every multi-segment query was pruning from zero in every segment.** On the
  15-segment corpus 17 of 28 queries were slower than Lucene while the merged
  index had them all faster. Each leaf got a fresh `TopDocsCollector`, so each
  one filled its own top-k before it could skip a block. Lucene's sequential
  `IndexSearcher.search` hands one `TopScoreDocCollector` to every leaf in
  turn. Fixed with `collector::LeafCollector` (a doc-base-shifting view of one
  shared collector) and `multi_segment::search_leaves_shared`; term and
  boolean queries went from 0.3-0.9x to 1.3-2.7x.
- **Constant-score queries expanded every segment's terms after the answer was
  already known.** Once a shared collector is full at the constant score with
  its threshold published, no later document can enter (equal score, higher
  doc id). `stream_constant_score_clause` now returns before expanding a
  clause's terms in that state: prefix/wildcard on the segmented index went
  from 0.35x to ~5x, regexp from 0.64x to ~9x.
- **A term was sought in the dictionary up to three times per segment**
  (reader-wide statistics, `try_seek_exact`, then `lazy_postings`, which
  seeks again). `FieldTerms::seek_term_state` / `lazy_postings_for` open
  postings from the state one seek returned -- Lucene's `TermStates`.
- **Numeric sort (`dv_sort`) called the queue for every document.**
  `TopFieldCollector::bottom_value`/`competes` let the scan reject a value
  that cannot beat the bottom inline, as `LeafFieldComparator.compareBottom`
  does, and `NumericReader::for_each_value` decodes the column a chunk at a
  time. On the segmented index Lucene is 8x faster than on the merged one
  because `NumericComparator` prunes with the sort field's points once its
  queue fills; `search_numeric_range_sorted_by_field_multi_segment_with_points`
  does the same (a later segment asks its BKD tree for the documents in
  `[min, bottom - 1]` and reads only those). 0.20x -> 3.0x.
- **The fuzzy DFA was determinized once per segment.** `FuzzyMatch::cached_dfa`
  builds it once per query, as `FuzzyQuery.getAutomata` does.
- **A wildcard-family query sought every expanded term twice** -- once in the
  automaton walk, again to open its postings. The walk decodes the postings
  pointers anyway; `FieldTerms::intersect_states`/`regexp_intersect_states`
  hand them out as `SeekedTerm`s and the constant-score paths open postings
  from them (`MultiTermQuery`'s rewrite keeps the same `TermStates`).
  `regexp body:t1[0-9]`: 0.66x -> ~1.07x.
- **A top-`n` points range sorted every match.** Lucene's `DocIdSetBuilder`
  sorts the whole set; a constant-score top-`n` only needs the `n` lowest doc
  ids and a count. `points_query::points_range_lowest_docs` selects them in
  linear time when the field is single-valued (`pointCount == docCount`, so no
  duplicates), and `points_range_top_n_multi_segment` stops visiting segments
  once the result is decided (`n` held, more than the 1000-hit threshold
  counted) -- the point at which `TopScoreDocCollector` reports its count as a
  lower bound. The doc-id radix sort also spreads its bits evenly over its
  passes: 23 bits as 11+11+1 sent every increment of the last histogram to the
  same counter, a serial store-to-load chain costing more than the rest of the
  sort.

- **A single one-document term sent a whole segment's disjunction to the slow
  path.** A pulsed term (`docFreq == 1`) has no `.doc` bytes, and the fuzzy
  and disjunction bulk scorers gave up on the segment when any leg was one
  -- on a many-segment index, most segments of a fuzzy expansion.
  `DocInput::singleton_cursor` opens such a term as a one-document cursor
  (document and `totalTermFreq` from the term metadata, as
  `BlockPostingsEnum.reset` does), and `lazy_postings_for` uses it. Fuzzy on
  the segmented index: 0.90x -> ~1.05x.
- **`regexp body:t1[0-9]` was the last query below Lucene (0.88x merged).**
  Two causes. Compiling the pattern -- once per query, as `RegexpQuery` does
  -- scanned a 256-entry row per DFA state in each of three pruning passes
  and hashed state sets with SipHash: 11% of the query. `Nfa::determinize`
  now hands `prune` the range transitions it already had and hashes with an
  Fx-style multiply (`automaton::SetHasher`), which is Lucene's own
  range-based shape. And the constant-score union that reads each term only
  up to a doc-id cutoff stepped with `next_doc`, which expands a bit-set
  block's 256 documents to read a dozen; it now steps with `advance(doc +
  1)`, which searches the bits (Lucene's `intoBitSet` never expands them
  either). 0.88x -> 1.18x.

### Indexing

- **Indexing measured 0.31x -- the one area that had never been compared**
  (the Java and Rust harnesses named the case differently, so the report
  never joined them). 92% of the time was probing the in-memory term hash:
  slots were taken from the *low* bits of an FxHash, which for short terms
  depend only on the first byte or two, so the benchmark vocabulary piled
  onto a handful of slots. Probing from the top bits (`inverter::home_slot`):
  44.8 us -> 4.1 us per document, **~3.3x Lucene**.
  `short_similar_terms_spread_over_the_table` pins the probe length (it fails
  with a displacement of 11 121 under the old slot choice).

### Postings

- **`advance` expanded every bit-set-encoded block into an array.** Lucene's
  `BlockPostingsEnum` answers `nextDoc`/`advance` on a bit-set block with
  `nextSetBit` and never materializes it. `LazyDocsCursor` now keeps such a
  block as its words (`BodyShape::Bits`) and finds the next set bit. A freqs
  cursor keeps `block_pos` as the document's rank (so `freqs[block_pos]`
  stays its frequency) from per-word cumulative popcounts filled at refill --
  Lucene's `docCumulativeWordPopCounts`, one lookup and one popcount; a
  docs-only cursor keeps no rank, as Lucene's does not, and `next_doc`
  recovers it when it expands the block. `next_postings` materializes on
  demand. `tz`/`t1` advance: 0.10-0.25x -> 0.6-0.8x.
- **Docs-only cursors decoded impacts nobody read** (level-1 spans) and wrote
  256 ones into the frequency array for every block. Both gated on what the
  cursor was opened for.
- **Every varint went through a generic `read_byte` loop.** `SliceInput` now
  overrides `read_vint`/`read_vlong` -- the whole value decoded from the
  slice when a maximum-length window is in view (a loop the compiler
  unrolls), the shared byte loop only near the end of the buffer or on a
  malformed value, so errors are unchanged -- and `read_i16`/`read_i64`. (A
  first version fast-pathed only one- and two-byte values and made longer ones
  a cold call: `vint` fell to 0.98x until this.)
- **The bit-set mode made sequential walks slower** (`postings_iter` t1/tz
  1.4-2.9x -> ~0.8x): finding each next set bit per `next_doc` costs more than
  reading an array. `next_doc` now expands a kept bit set once, on first use;
  `advance` keeps searching the bits.
- **`advance` was one large function.** The in-block case -- target at or
  below the decoded block's last document -- is now a small inlined fast path
  (`LazyDocsCursor::advance`), everything else `advance_slow`.
- **An earlier write-up blamed the per-call API shape for `advance` at ~0.6x.
  It was wrong.** A second pass found five concrete causes, and with them
  fixed every `postings_adv` case is at or above Lucene:
  - *A consecutive block was expanded and scanned.* A term in nearly every
    document (`t0`: 99.94%) is almost all `bitsPerValue == 0` blocks, which
    Lucene keeps as a bit set with the first 256 bits on and answers with
    `nextSetBit`. The cursor filled a 256-entry array and searched it; it now
    keeps the bit set too. `t0_gap8`/`gap64`: 0.6x -> 1.0-1.1x.
  - *`advance_slow` scanned the rest of the block before leaving it.* With the
    target past the block's last document the scan can only come up empty;
    Lucene's `target > level0LastDocID` goes straight to the skip data. Half of
    what a long advance cost. `t0_gap1024`: 0.6x -> 1.3x.
  - *A bit-set refill counted its bits with a saturating fold* -- a branch per
    word that chained the popcounts. At most 8192 bits cannot overflow a
    `u32`, so a plain sum is exact and pipelines. `tz_gap1024`: 0.86x -> 1.1x.
  - *The next header was a cache miss.* Its offset is known as soon as the
    landing block's header is parsed, so `SliceInput::prefetch` loads it while
    the body decodes; a docs-only walk skips headers in a tight loop with the
    cursor's state in locals (`skip_level0_headers`), and `read_vint15`/
    `read_vlong15` inline.
  - *The in-block search waited on a vector mask at every step.* Lucene's
    Panama `findNextGEQ` tests the element eight ahead with a plain,
    predictable branch and only then counts (Lemire's V1 step);
    `simd::find_next_geq_v1` does the same for two steps, then counts the rest
    without an early exit (`simd::count_less_than`), as does the landing in a
    freshly decoded block, where an early-exit scan ends on a branch that
    cannot be predicted.
- **`next_position` lost ~15 cycles on every document's first position.**
  LLVM fused `doc_left -= 1` and the position add into one two-lane vector op;
  its 64-bit load spanned the two separate 32-bit stores `start_doc` makes, a
  store-forwarding failure. `doc_left` is now a `u64`, which stops the fusion.
  `positions` t2s/tz: 0.86-0.91x -> 1.4-1.7x.

### Codecs and kernels

- **Stored fields (0.83x)**: the LZ4 decoder did a variable-length
  `memmove` per sequence. `lz4::decompress_slice` moves short literals and
  matches as fixed 16- and 8-byte copies inside the block's own bounds (the
  reference decoder's "wild copy"), in safe code. 1.32x.
- **Float vectors (0.30-0.40x)**: an accumulator array LLVM would not
  vectorize. `lucene_util::simd::{dot_f32, square_distance_f32,
  cosine_parts_f32}` are explicit AVX2+FMA with Panama's layout (four 8-lane
  accumulators), with scalar specifications of the same fold order that the
  tests require to agree bit for bit. Byte vectors multiply in `i16` so LLVM
  pairs them into `vpmaddwd`. 1.0-1.5x.
- **Doc values (0.51x sequential)**: per-document `Result<Option<i64>>`
  through three range checks. `PackedLongs::decode_range` decodes a run with
  one check and a branch-free loop per bit width (`NumericReader::for_each_value`,
  which the range and sort scans now use). 1.31x. Random access folds the
  document and packed-window bounds into one precomputed limit and keeps
  `value` small enough to inline (`value_slow` holds every other shape).
- **Bitset `or` (0.46x)**: an explicit AVX2 kernel (`simd::or_words`), eight
  registers per step, peeling scalar words until the destination is 32-byte
  aligned so the loop uses aligned loads and stores (the remaining gap had
  been split loads from 8-byte-aligned `Vec<u64>` storage). 1.00x.
- **`DirectReader` (0.48x on one-bit reads, and worse once measured fairly)**.
  The free `direct_reader::get` re-validates the width and does its
  arithmetic with the width as a variable. The first comparison flattered it:
  one Java `walk` call site served all fourteen widths, so C2's type profile
  went megamorphic and every width from 4 bits measured a flat ~2.3 ns of
  virtual dispatch. `DirectReaderMicro` now runs one JVM per width, and
  against monomorphic Lucene the generic read was 0.57-0.94x. Lucene's answer
  is a class per width; this port's is `DirectReader::with_width`, which runs
  the caller's loop over a `FixedWidthReader<B>` compiled per width, reading
  through `lucene_util::packed_longs::FixedPackedLongs`: one comparison, an
  unchecked load sized to the width (`readShort`/`readInt` where those
  suffice -- an eight-byte load at a three-byte stride splits cache lines),
  and a byte offset computed directly for byte-aligned widths. (A per-call
  `match` on the width measured slower than the generic formula: the jump is
  not hoisted.) The Rust harness also summed through memory around every
  read; it now reads 4096 values per clock check into a local, as Java's
  does. 1.08-1.33x. No engine read path uses it yet (see `docs/parity.md`).
- **Points (0.72x large ranges)**: two zeroed `Vec`s per leaf for the doc ids.
  `read_doc_ids_into` reuses one buffer for the whole walk; the packed
  `BPV_21`/`BPV_24` words are bulk-copied into that buffer, the low-bit ids
  assembled from them, then the words shifted down in place -- no scratch
  array. (A first version read each word through four checked byte loads
  and made large ranges 4x *slower*; the vectorizable bulk copy is the fix.)
  The doc-id sort (`sort_dedup_doc_ids`) builds all digit histograms in one
  pass, skips passes whose digit is constant (as `LSBRadixSorter` does) and
  scatters with unchecked stores.
- **Regexp/wildcard/fuzzy term walks** seek past dead dictionary branches with
  a per-state list of live byte ranges (`ByteDfa::next_live_byte`) instead of
  stepping all 255 bytes above the dead one.

## Regexp engine (follow-up)

The sweep's regexp query (`t1[0-9]`) has a literal prefix, the easiest shape
for any engine. Nine more shapes (q29-q37 in `benchmarks/queries.tsv`) were
added -- leading wildcard, broad class, alternation, a wildcard middle, no
literal at all, "contains" and suffix patterns -- and the regexp path was
rebuilt around them. Results, `benchmarks/.results/round13-regexp.txt`
(`java_time / rust_time`; no query of the 37 slower than Lucene on either
index):

| query | pattern | merged: before | merged: after | segmented: after |
|---|---|---|---|---|
| q26 | `t1[0-9]` | 1.01x | 1.63x | 18.7x |
| q29 | `.*z` | 1.45x | 2.48x | 16.6x |
| q30 | `t[0-9a-f]+` | 9.2x | 10.3x | 27.7x |
| q31 | `(t1\|t2)[a-z]` | 500x | 793x | 877x |
| q32 | `t.*9` | 1.47x | 2.55x | 14.2x |
| q33 | `[a-z][0-9]{2}` | 303x | 461x | 522x |
| q34 | `.*1.*2.*` | 1.15x | 2.15x | 16.0x |
| q35 | `.*zz.*` | 1.10x | 7.95x | 135x |
| q36 | `.*9x1.*` | 1.02x | 94x | 2 813x |
| q37 | `.*a0` | 1.08x | 18.6x | 398x |

What changed, in the order it paid:

- **The DFA became exact.** `&` was approximated by its left operand and
  `<n-m>` by any run of digits, so every term the automaton accepted went
  through the backtracking matcher as well. `&` is now a product automaton
  and `<n-m>` a digit automaton (`Automata.makeDecimalInterval`'s language),
  checked against the matcher over every digit string up to five wide.
- **`IntersectTermsEnum`, ported** (`blocktree::DfaIntersect`). The previous
  walk fed every term, found by comparing it with the one before, through the
  automaton, and could only skip by re-seeking from the root. The lockstep
  walk keeps the automaton state at each block's prefix and runs only an
  entry's suffix bytes, in place; a dead sub-block is never loaded; floor
  blocks are skipped by their lead bytes using the trie node's floor data;
  and an entry sorting past the last byte the prefix state can take ends the
  block. Same-binary A/B against the old walk: 1.3-2.0x on every shape.
- **`CompiledAutomaton.ALL`.** `.*` and `@` enumerate every term, ill-formed
  UTF-8 included, as Lucene does; the byte DFA rejected those terms. Found by
  the new Lucene-written fixture, not by reading.
- **Accept-all-suffix states.** A state whose language is exactly the
  well-formed UTF-8 strings (found once, by a product with the canonical
  all-UTF-8 automaton) answers a term entry with a UTF-8 validator instead of
  the table. Lucene's open PR #16564 does this only for full-alphabet
  self-loops and leaves out `UTF32ToUTF8` automata -- regexp and wildcard.
- **A term n-gram index** (`term_ngram`, no Lucene counterpart). A pattern
  with no literal prefix but forced literal text (`.*9x1.*`, `.*a0`) is
  answered from the terms containing its bigrams/trigrams, verified by the
  automaton, instead of a walk over the whole dictionary: q35-q37 went from
  1.0-1.1x to 8-94x (merged) and 135-2 813x (segmented). Built per field after
  two dictionary-wide walks, only for fields up to 2M terms, streamed; 49 ms
  and 6 MB for the benchmark's 200 000-term field.
- **A compiled-pattern cache**: once per pattern for every segment (it was
  per segment), and process-wide by pattern text for repeated queries.
- **A lazily determinized automaton** (`automaton::LazyDfa`,
  `NFARunAutomaton`'s role) for patterns too large to determinize, which
  Lucene rejects by default; past its entry budget the query fails the same
  way. Previously these fell back to the backtracking matcher over every
  term.
- **Byte classes**: bytes no state distinguishes share one table column.

Verification: `crates/lucene-codecs/tests/regexp_intersect_fixtures.rs` runs
38 patterns over a 65 000-term dictionary Lucene wrote (floor blocks, nested
sub-blocks, multi-byte and ill-formed terms) through the lockstep walk, the
lazy automaton and the n-gram index, against what Lucene's own
`IntersectTermsEnum` enumerated, and sweeps single-byte corruptions of the
term index and terms file to check every walk ends. That sweep is what caught
a real defect: a corrupt term index could point the walk back into blocks it
had already loaded, and `check_index`'s equivalent sweep spun for ten hours
until the walk was made to refuse loading a block twice.
