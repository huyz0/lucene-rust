# M7 benchmarks, October 2026 -- the new queries, similarities and writers against Lucene 10.5.0

**Goal:** close M7's "no slower than Lucene on its benchmark" criterion. Every
query family, similarity and writer M7 ported gets a `scripts/bench-micro.sh`
pair -- the same operation on this port and on Lucene 10.5.0, over the same
bytes -- and every ratio below 1.0 is either optimised away or explained.

## Method

- **Machine:** a 4-vCPU cloud VM (Intel Xeon @ 2.10 GHz, no hybrid cores,
  no hardware performance counters exposed), Linux 6.18. Not the
  `docs/benchmarks/environment.md` machine: ratios, not absolute times, are
  the result.
- **Builds:** rustc 1.97.1, `x86-64-v3` (`.cargo/config.toml`), the
  `benchmarks/rust-runner` release profile (fat LTO); OpenJDK 25.0.4.1 with
  `--add-modules jdk.incubator.vector`; the Lucene 10.5.0 jars.
- **Protocol:** `scripts/bench-micro.sh --bench <name>`, unchanged: both
  engines pinned to CPUs 0-1, three interleaved repetitions, the noise floor
  measured per run (same engine against itself); a ratio inside it is printed
  with `~` and is not a result. Each bench was started only once the
  one-minute load average was below 0.6 (it rose to 1.0-1.5 during a run,
  from the benchmark itself).
- **Same answers, checked:** every new pair also prints a `#check` line per
  case -- an FNV-1a 64 digest of the hits' doc ids and score bits (doc ids
  alone for the field sorts, written bytes for the writers, query strings
  for `QueryBuilder`) -- and `scripts/bench-micro-report.py` fails the run
  on any difference. Every run of the new pairs below reported **0
  mismatches**: both engines returned the same answer on every case they
  were timed on. (`term_dict_write` and `analysis` predate the check; their
  output is covered by their differential tests.)
- **Inputs:** `m7_fixture` runs every search `GenM7Queries` records over its
  three fixture indexes (180, 2,500 and 17,000 documents, so it weighs a
  query's fixed costs -- rewrite, statistics, scorer construction -- as much
  as its per-document loop); `m7_corpus` runs 47 queries of the same grammar
  over the one-segment, million-document benchmark corpus
  (`benchmarks/.corpus/merged`); `similarity` the corpus under each
  similarity and the span queries; `sort_pruning` the field-sorted rows of
  `benchmarks/queries.tsv`; `query_builder` `QueryBuilder` over
  `StandardAnalyzer`; `stored_fields_write` `GenStoredFieldsDeflate`'s
  documents; `term_dict_write` and `analysis` the existing pairs, re-measured.

Ratios are `java_time / rust_time`: **above 1.0 means this port is faster.**

## Closing the last three (second pass, 2026-10-01)

The first pass left three cases below 1.0 outside their noise floors:
`CombinedFieldQuery` and `IndriAndQuery` on the corpus, and
`StandardTokenizer` on multilingual text. All three are now ahead of
Lucene. Hits and score bits are unchanged: every differential test passes
(`cargo test -p lucene-search` in debug and release, `-p lucene-analysis`
including the 17,073-case conformance fixture and the 4.89 MB corpus test
with the jars), and every bench run reported 0 `#check` mismatches.

**Machine.** The VM was replaced between passes. The new one is also 4
vCPUs, but an Intel Xeon @ 2.80 GHz where Lucene's Panama provider now
reports `preferredBitSize=512`. Same protocol as above: CPUs 0-1, three
interleaved repetitions, each run started at a one-minute load below 0.6.
Ratios from the two machines are not directly comparable. The "before"
column is the first pass's figure, and the analysis row's in-brackets
figure is this machine's own before-run.

| case | before | after | noise | change |
|---|---|---|---|---|
| `m7_corpus` `combined_field` | 0.78x | **2.09x** (9.7 ms vs 20.3 ms) | 1.20x | windowed bulk scorer, memoised combined norms, batched BM25 |
| `m7_corpus` `indri` | 0.85x | **2.87x** (4.3 ms vs 12.3 ms) | 1.14x | an all-terms Indri AND bulk-scored as a docs-only union |
| `analysis` `tokenizer_multilingual` | 0.80x (0.93~ here) | **1.41x** | 1.19x | the JFlex scanner reads UTF-8 directly |
| `analysis` `standard_multilingual` | 0.81x (0.94~ here) | **1.39x** | 1.24x | same |
| `analysis` `tokenizer` | 0.94~ (1.11~ here) | **1.89x** | 1.39x | same |
| `analysis` `standard` | 0.98~ (1.21~ here) | **1.69x** | 1.40x | same |

What changed:

- **`CombinedFieldQuery`** (`exec/extended.rs`). The old profile showed
  three costs: combining the norms (25%), BM25's divide behind a
  `dyn SimScorer` call (16%), and the disjunction's per-document heap
  walk. Each now has a fix:
  - *Norms:* with one or two fields whose norms are dense, one byte per
    document, the combined norm depends only on the pair of norm bytes.
    `DenseMemo` computes it once per distinct pair, with the same
    arithmetic, and remembers it (a 64K-entry table).
  - *Scoring and the disjunction:* a top-level query whose term is in at
    most two fields gets its own bulk scorer, `CombinedWindow`. For each
    window of 4,096 documents it does four passes:
    1. Copy each member's postings in a decoded block at a time
       (`nextPostings`), adding `freq * weight` into the document's slot.
    2. Gather the live documents in order, with their norms.
    3. Score the whole batch as one loop. For BM25 the loop uses
       `BM25Scorer`'s exact `weight - weight / (1 + freq * cache[norm])`
       through `SimScorer::bm25_parts`, with no call per document, so it
       vectorises. Other similarities go through `score_bulk`.
    4. Collect every document.
  - *Why only two fields:* `float` addition commutes, so two members' sum
    does not depend on the `topList()` order. Three or more members still
    run on the scorer tree, which keeps that order.
- **`IndriAndQuery`** (`exec/bulk.rs::bulk_indri_terms`). Every clause
  being a plain term means no sub-scorer is an `IndriScorer`, so every
  document scores exactly 0. `IndriDisjunctionScorer` ignores the minimum
  competitive score, so Lucene collects every live document of the union
  at 0. That is `Bulk::Union` over docs-only cursors: no frequency is
  decoded and no score is computed, because none is read. With only one
  term present in a segment, the query is that term and is scored
  normally, so this path is declined.
- **`StandardTokenizer`** (`standard/tokenizer_impl.rs::get_next_token_utf8`).
  - *Where it applies:* a plain string input (`CharReader::whole_text`,
    answered by an unread `StrReader`). The scanner walks the UTF-8 bytes
    directly, with the same DFA and the same `zzCMap` per code point. It
    keeps each position in UTF-16 code units beside its byte position, so
    `yychar`, `yylength` and the offsets are Java's `char` offsets. The
    term is then set from the `&str` slice, with no UTF-16 round trip.
  - *What it saves:* the UTF-8-to-UTF-16 transcode (14% of the
    multilingual profile) and the UTF-16-to-UTF-8 term copy (15%).
  - *The buffer rule:* the one behaviour `zzRefill` adds is its buffer of
    `maxTokenLength` code units. A run longer than the buffer is cut, and a
    supplementary character whose high surrogate would land in the
    buffer's last unit is held back. Both reduce to one rule from the
    match's start: only code points that fit whole in `maxTokenLength`
    units are visible.
  - *How it is checked:* a new test, `utf8_scan_matches_the_utf16_scan`,
    runs both scans over every fixture text at buffer sizes 1, 2, 3, 4, 5,
    7 and 255, plus supplementary-character runs. Char filters and other
    readers keep the UTF-16 path.

## Closing `mtq_csb` (third pass, 2026-10-01)

*Supersedes the `mtq_csb` paragraph above.* Profiled one query at a time,
three of the four queries were behind (`PF body t1` 0.80x, `A body t3.*`
0.83x; the range about even). A short prefix there expands to 47,989 terms
holding 14.6 million postings. Three changes closed the gap. Hits and score
bits are unchanged, with 0 `#check` mismatches.

- **Stream the expansion, as Lucene does** (`exec::multi_term::StreamedTerms`).
  - *Before:* every matched term was collected first: its bytes, its
    metadata, then a selection of the 16 highest-`docFreq` terms over the
    whole list, and a move of the rest. That was about a fifth of the
    profile: allocator calls, page faults, and unmapping a multi-megabyte
    `Vec` on every query.
  - *Now:* the port consumes the terms as `MultiTermQueryConstantScoreBlendedWrapper`
    does. A term with `docFreq <= 512` goes straight into the
    `DocIdSetBuilder`. The others are offered to a 16-entry priority queue,
    and whatever it drops goes into the set too. A term that covers every
    document with the field ends the walk. This applies to prefix,
    wildcard, regexp, `AutomatonQuery` and term range, under both the
    blended and the plain constant-score rewrite. A term set, already a
    list, is pushed through the same path after its terms are sought.
  - *Behaviour kept:* `UnionBuilder` starts sparse and upgrades to the
    pooled bit set past `maxDoc >> 7`, as Java's builder does.
- **Decode a tail block straight into the doc buffer**
  (`SliceInput::read_group_vints_i32`). For a term with `docFreq` below 256,
  the tail block is the only decode it ever does. It went through a `u64`
  staging array that was zeroed (2 KiB) and copied out of on every term.
- **A tail block's last group no longer takes the per-value `Result` path.**
  When the slice ends with the term, the last group has no 17-byte window
  after it. It is now decoded directly from its own bytes whenever they are
  all present. A group that is cut short still goes through the default
  decoder, so errors and their offsets are unchanged.

One query at a time after the change: `PF body t1` 1.16x, `R body t10 t20`
1.19x, `A body t3.*` 1.14x. `W body t?3`, which was never behind, read
1.6x in the profiling runs. The full suite on this machine, on the final code (noise floor 1.21x,
median 1.49x, 0 `#check` mismatches):

- **The two rewrites:** `mtq_csb` **1.35x**, `mtq_cs` 1.37x
  (`mtq_csbool` 1.41x).
- **The rest:** at or above 1.0 or inside the floor. Bayesian 1.54x,
  blended 1.22x, combined field 1.89x, DV range 5.14x, fuzzy 1.49x,
  index-or-DV 1.88x, Indri 2.74x, log-odds 1.12~, `mtq_dv` 7.87x,
  `mtq_sb` 1.09~, `mtq_ttb` 3.41x, `mtq_ttbf` 2.62x, `mtq_tts` 1.38x,
  multi-phrase 1.28x, n-gram phrase 1.50x, explicit-position phrase 0.99~,
  points 2.10x, synonym 1.13~.

A run between the streaming change and the review fixes (the 512
threshold, the dense-term shortcut) read `mtq_csb` 1.19x and `mtq_cs`
1.23x, with the same four cases inside the floor.

The last M7 case is therefore no slower than Lucene.

## The bit set pool regression (2026-10-03)

*`m7_fixture`'s `points` and `index_or_dv` rows above (1.39x, 2.32x) are the
first pass's; this is what happened to them after, and the fix.*

A run on 2026-10-03 measured `m7_fixture` `points` at 0.04x and
`index_or_dv` at 0.18x. Confirmed on 5b6d03d (0.04x, 0.17x; Rust 296 us
and 224 us an iteration against Lucene's 12 us and 39 us), every other case
unchanged. This machine is the 2.10 GHz one again.

- **Where.** The prime suspects were the M9 points changes (lazy
  `PointTreeNode`, `IntersectVisitor::grow`, the leaf box check), but the
  M9 range was already slow at its start (c5be7e0). Timing the two cases
  alone (`MICRO_CASE`) at older commits: 2614910 (the first pass) 10 us and
  19 us, 335ec37 8.5 us and 21 us, **8f646fc 89 us and 101 us**, and every
  commit after it slow. 8f646fc is "pool the multi-term clause's bit set
  across queries" from the third pass. That pass re-ran `m7_corpus` and not
  `m7_fixture`, and on the corpus's one large segment the effect is
  invisible, so M7 closed with it in.
- **Why.** 8f646fc made every `CachedSet::Bits` give its words to the
  per-thread pool when dropped. Point-range clauses build such sets too, and
  no later query takes sets of their lengths back, since only the
  multi-term union and the sort competitive iterator call `take`. The pool
  was bounded by bytes alone, 8 MiB, which is about 350,000 sets of a
  180-document segment. `give` summed the whole list on every call, and
  `take` scanned it. Over a run the list grew to that size, so each query
  paid two walks over hundreds of thousands of entries. The callgrind
  profile showed no instruction hot spot, only `give` and the allocator,
  because the cost was spread across the walk. It also grew with the run:
  296 us inside the full suite against 92 us alone.
- **Fix** (`lucene-search/src/bit_set_pool.rs`, f8ce546 and c86c9c7):
  - At most 32 sets as well as 8 MiB.
  - The oldest set is evicted when a new one would pass either limit,
    rather than the newest being refused.
  - A running byte total replaces the sum.
  - A set is cleared when it is taken, not when it is given. The first
    version of the fix still cleared on `give`. That was a memset of the
    whole set for sets nobody takes, and against 5b6d03d it read
    `geo_points_contains` 0.78x and `geo_polygon_disjoint` 0.90x, Rust
    side. Clearing on `take` brought both back to 1.01x and 1.02x.
- **Guard.** Unit tests: a thousand sets of lengths nothing takes leave the
  pool at its count limit, a set a later query wants survives eviction and
  comes back cleared, and a set that would pass the byte limit evicts the
  oldest. These test the bound itself, with no timing.

## `span_near_ordered` (2026-10-03)

The one case the regression pass left below 1.0 (0.90x). Profiled
(`perf`, `MICRO_CASE=span_near_ordered`, the `similarity` bench's
`SpanNearQuery([t0, t1], 0, inOrder)` over the million-document corpus):
55% of the time in `exec::span::emit` -- per candidate document, each
term's positions copied into a list of `(start, end)` spans, the
`NearSpansOrdered` walk pushing every match as `(start, end, width)`, and
`freq_of` summing them -- and 15% decoding the positions. Java's
`NearSpansOrdered` walks the term spans in place.

**Fix** (`lucene-search/src/exec/span.rs`): an in-order `SpanNearQuery` of
terms alone is scored straight from the positions (`ordered_terms_freq`):
the same walk as `near_spans::ordered_walk` over `[p, p + 1)` spans, each
match's `1 / (1 + width)` added as found, in emission order -- the same
float sum, bit for bit -- and, at slop 0, where every match has width 0 and
adds exactly 1, the count of matches (up to 2^24, where the `float` sum
stops growing). A unit test compares it with `emit` + `freq_of` on 3,000
random documents of 2-10 clauses (repeated terms, slops 0-6), seen to fail
when the slop test is off by one; the span differential fixtures
(`span_query_fixtures`, `similarity_search_fixtures`, highlighting) pass.

Interleaved A/B, Rust side: 223 -> 177 ms per query. `bench-micro.sh
--bench similarity` (noise floor 1.10x): `span_near_ordered` **1.36x**,
the other span cases 1.26x-1.57x (`span_classic` 1.44x, which includes
it), every similarity 1.30x-4.56x.

## Below 1.0 in the first pass, and why

*Superseded for the three cases below by "Closing the last three" above; kept as the record of the first pass's profiles.*


Three cases stay below 1.0 outside their noise floors. Each was profiled;
none is a missing algorithm, and each family is ahead of Lucene on the
fixture indexes (the same code over 180-17,000 documents):

- **`CombinedFieldQuery` over the corpus, 0.78x** (1.74x on the fixtures).
  Lucene 10.5.0's `CombinedFieldScorer` has no impacts and no
  `setMinCompetitiveScore`, so both engines score every document matching
  either field; the first query (`t1` over `body` and `title`, about two
  thirds of the per-query time) is 51.7 ms against 33.9 ms. The profile is
  the per-document work Java also does: `MultiNormsLeafSimScorer`'s norm
  (two norm bytes, `LENGTH_TABLE`, `Math.round`, `intToByte4`) 23%, the
  BM25 `score` (a dynamic call ending in a dependent divide) 16-19%, the
  two-member disjunction 21%, the collector 11%. Inlining the norm read and
  table-encoding the combined length were tried and did not move it (and
  were dropped); what is left is code generation on a dependency chain the
  JIT schedules better.
- **`IndriAndQuery` over the corpus, 0.85x** (1.41x on the fixtures). An
  `IndriAndQuery` of plain terms scores every document `0` (`scoreDoc` folds
  only sub-scorers that are `IndriScorer`s), so the query is a two-term
  disjunction walked to the end with no pruning -- `IndriDisjunctionScorer`
  reports a maximum of 0 and ignores the minimum competitive score, in both
  engines. One query (`t1` or `t2`, 35.3 ms against 23.7 ms) carries the
  gap; the other two are 0.89x and 1.34x. The profile is that walk: the
  `DisjunctionDISIApproximation` (34%), each member's `nextDoc` (26%), the
  collector (17%). Here every layer is a dynamic call -- the Indri scorer
  over boxed child scorers, each a `TermScorer` over the postings cursor --
  where the JIT inlines Java's monomorphic `DisiWrapper.iterator.nextDoc()`.
- **`StandardTokenizer` on multilingual text, 0.80x (0.81x through
  `StandardAnalyzer`)**; ASCII text is inside the noise floor (0.94~,
  0.98~). The difference is the input: Lucene's benchmark hands the
  tokenizer a Java `String`, already UTF-16, which `StringReader` copies;
  this port's input is a Rust `&str`, and the JFlex scanner -- ported table
  for table -- reads UTF-16, so `StrReader::read` transcodes UTF-8 to UTF-16
  inside the timed region: 16% of the multilingual profile, about the whole
  gap (2-3 byte characters are the slow branch). The equivalent Java cost
  is paid when the text is decoded into a `String`, outside Lucene's timed
  region. The term attribute's UTF-16-to-UTF-8 step (13%) is the same work
  Lucene does in `getBytesRef`. Two attempts at a faster transcoder (a
  `chars()` loop, a slice-pattern decoder) measured slower than the current
  one and were dropped.

Inside their noise floors (not results either way): `m7_corpus`
`phrase_positions` 0.96~ and `mtq_csb` 0.98~; `m7_fixture` `mtq_sb` 0.91~;
`sort_pruning` q80 0.92~.

## What changed to get here

The first quiet runs of this pass, before the changes below, had these
below 1.0: `m7_corpus` fuzzy 0.56x; `m7_fixture` KNN seeded 0.38x and patience
0.71x on `m7_knn_index`, vector similarity 0.84x on `m7_queries_index`; `term_dict_write`
`ids_1m` 0.55x; the tokenizer 0.81-0.87x. The changes, each re-run against
its differential tests:

- **Fuzzy (0.56x to 1.25x).** The Levenshtein DFA is determinized over
  bitset subsets with each NFA state's epsilon closure computed once
  (`Nfa::determinize_bitsets`), its lenient UTF-8 continuation states are
  shared per target, and byte classes are found from the rows' range
  boundaries: a two-edit automaton went from 1.76 ms to 0.69 ms to build.
  When the top-terms queue lowers the edit budget (`bottomChanged`), the
  block-tree walk now restarts over the smaller automaton
  (`FuzzyMatch::cached_compiled_dfa_within`) instead of only narrowing the
  exact test -- Java's `getAutomatonEnum(maxEdits, lastTerm)`.
- **KNN (on `m7_knn_index` seeded 0.38x to 1.39x and patience 0.71x to
  1.15~; vector similarity on `m7_queries_index` 0.84x to 1.10~).** The
  benchmark grammar reopened the vector readers (checksumming every file)
  per query, where an `IndexReader` holds them; they are now opened once.
  The seed query's `FieldExistsQuery` and `MappedDISI` stopped reopening the
  vector values per ordinal, and the accept-ordinal set is built from the
  document side -- the deleted (or filtered) documents looked up in the
  field's doc-to-ordinal iterator -- instead of translating every ordinal.
- **Term dictionary writes (0.55x to 1.23x on `ids_1m`).** One pass over each
  term's postings (`validate_field` gathers the statistics the block tree,
  `encodeTerm` and `.tmd` read), no `Option<PositionLayout>` slot per term
  of a docs-only field, and the block tree borrows the previous term rather
  than copying it.
- **`StandardTokenizer`.** The JFlex transition table flattened into one
  `[state][class]` row of 32 with the accepting/final attributes packed into
  each entry, and an ASCII term narrowed on the stack.
- **Earlier in this pass** (before the run that opened this list): the span
  scorer rewritten as a cursor-driven, allocation-free tree; `SynonymQuery`'s
  impacts (`mergeImpacts`, so `TOP_SCORES` skips blocks as Java's
  `ImpactsDISI` does); MTQ scoring rewrites through
  `BooleanQuery`'s `MaxScore`; doc-values rewrites cached as Java's
  `ConstantScoreQuery` wrapper is; doc-values ranges enumerated with
  `seekCeil`; postings `into_window` and group-varint fast paths; the
  zlib port's `longest_match` comparing eight bytes at a time.
